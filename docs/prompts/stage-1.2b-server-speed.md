# Этап 1.2б – ускорение сервера кабинета: меньше запросов в удалённые БД

> Промпт для worker-сессии. Автор – мастер-чат партнёрки, 2026-09-25.
> Рекомендуемая модель: Sonnet. Удалить файл после приёмки этапа.
> Разрешено владельцем 2026-09-25 как исключение из правила «только UX».

## Правила сессии

- Одна сессия, **без суб-агентов**. `app/Models/JoomlaCoupon.php` –
  1650 строк, читай фрагментами по нужным методам.
- **Git-мутаций не делаешь** (add/commit/switch/stash запрещены).
  Read-only `git status/diff/log` – можно.
- Репо в WSL: `~/dev-partner`. Команды – через
  `wsl -d Ubuntu-22.04 bash -lc '...'`, не Windows-git по UNC (CRLF).
  Команды с кавычками или `$` – пиши в `.sh`-файл в `/tmp` WSL и запускай
  файлом; после работы удали их.
- PHP/artisan – только в контейнере: `docker exec laravel_backend php artisan ...`.
- Меняешь **только серверный код партнёрки** (`app/`, при необходимости
  `config/`). **Нельзя:** фронт `resources/js/` (его параллельно правит
  другая сессия), миграции и схемы БД, основной бэкенд Avicenna, флаги
  `PARTNER_*`, `.env`. Новые composer-пакеты не ставить.
- ☠️ **Логику минта купонов не трогать** (`createCoupon`, dual-write,
  `AvicennaBackendClient::mintPartnerCoupon`) – см. `docs/operations.md` §3–4.
- Все БД локально – **удалённые** (Beget): своя `dev-partner` и dev-копия
  Joomla `AviDev`. В БД **только SELECT**. Никаких записей, даже тестовых.
- Не трогай то, что вне задачи (безопасность, `console.log`, опечатки) –
  найденное пиши в отчёт. Отдельно известно: PHP-warning
  `"continue" targeting switch` в `JoomlaCoupon.php:1467/1480` – **не
  чинить в этом этапе**, только не сломать.
- Комментарии в коде – по-русски.
- Стек: Laravel 12, PHP 8.3 (контейнер и прод). Проверь версии в
  `composer.json`/`composer.lock` перед использованием API.

## Контекст и замер «до»

Прочитай `docs/cabinet-map.md` §2 и §4а. Кратко:

- Один запрос к удалённой БД стоит ~101 мс на проде и ~175 мс на локалке,
  подключение – ~255/500 мс.
- `GET /api/user/business-data` (`UserCouponController::data`) у партнёра
  с 5 купонами делает **39 SQL в Joomla + 6 в свою БД + 2 HTTP в
  основной бэкенд**: локально 9–11 с, на проде ~5–6 с, и растёт на
  ~7 SQL с каждым купоном. Причина – циклы «запрос на купон» и повторные
  одинаковые запросы из разных методов `JoomlaCoupon` (`getUserCoupons`,
  `joomlaUser`, `getPpOrders` в цикле, `credits`, `withdrawals`,
  `oldPromocodBalance`, `getUserPercentCouponsSummary`…).
- Тем же страдают `GET /api/user/coupons` (`UserCouponController::index`,
  ~3 с) и остальные методы `UserCouponController`.

## Что сделать

1. **Эталон ДО правок.** Сначала, ничего не меняя, сними ответы
   `business-data` и `/user/coupons` для 3–4 партнёров с разным числом
   купонов (подбери по dev-БД SELECT'ами: без купонов, 1–2, 5+, с
   бонусными, с заказами нового сайта). Вызов без токенов – через tinker:
   `Auth::login($user); request()->setUserResolver(fn() => $user);`
   и вызов метода контроллера. Сохрани JSON в `/tmp/ppm-before/<id>.json`
   (в WSL) и заодно посчитай число SQL по коннектам (`DB::listen`) и HTTP
   (`Illuminate\Http\Client\Events\ResponseReceived`) и время.
   ⚠️ `getUserCoupons`/`joomlaUser` могут **создать** пользователя в Joomla,
   если его нет, – бери только партнёров, у которых Joomla-пользователь уже
   есть (проверь SELECT'ом по email в `jm_users`).
2. **Убрать N+1 и повторы в Joomla.**
   - Запросы «в цикле по купону» (`getPpOrders` и подобные) заменить
     выборкой по всем купонам партнёра разом (`whereIn`) с группировкой в
     PHP. Публичные сигнатуры методов, которыми пользуются другие места,
     сохранить (можно добавить пакетный метод рядом и перевести на него
     `data()`/`index()`).
   - Одинаковые запросы за один HTTP-запрос (Joomla-пользователь, список
     купонов, запись `avicenna_user_coupons` и т. п.) – мемоизировать на
     время запроса (статический кеш в классе по ключу пользователя, как
     уже сделано у `loadBackend()` через `self::$backendCache`).
   - `loadBackend()` уже кеширует HTTP в бэкенд в рамках запроса – не
     ломать.
3. **Кеш ответа `business-data` на 60 секунд** для каждого пользователя:
   `Cache::store('file')` **явно** (дефолтный кеш на проде – `database`,
   то есть та же удалённая БД). Ключ – по id пользователя (учти
   impersonate: ключ по фактическому `$request->user()->id`). Сброс кеша
   пользователя после действий, меняющих его данные:
   создание купона, заявка на выплату, загрузка чека, и админские
   действия с выплатами/реквизитами этого пользователя
   (`PayoutRequestController`, `RequisiteController` – найди все места,
   где меняются его выплаты/реквизиты). Сделай один хелпер сброса и зови
   его оттуда. Начисления из основного бэкенда при этом могут
   запаздывать до 60 с – это приемлемо, упомяни в отчёте.
   Если сочтёшь полезным такой же кеш для `/user/coupons` – сделай с тем
   же сбросом.
4. **Эталон ПОСЛЕ.** Повтори п. 1 и сравни JSON с эталоном. Ответы
   должны совпасть **полностью** (порядок элементов в массивах – тоже;
   если порядок меняется неизбежно – объясни почему и что фронт от этого
   не зависит). Кеш при сравнении выключи/сбрось, чтобы сравнивать
   реальную выборку.
5. **Сессии и кеш Laravel** (`SESSION_DRIVER=database`,
   `CACHE_STORE=database`) – **не менять**. Только оцени: где используются
   сессии (API на Sanctum-токенах, `web`-роуты SPA, соц-вход через
   `session('social_user')`), безопасно ли на проде перейти на `file`, и
   опиши в отчёте, что должен сделать владелец в прод-`.env`.
6. **Доки в том же изменении:** в `docs/operations.md` – короткий раздел
   про кеш `business-data` (где лежит, TTL, когда сбрасывается, как
   сбросить вручную); в `docs/cabinet-map.md` §4а – строка «после» с
   цифрами.

## Проверка

- `docker exec laravel_backend php artisan route:list` работает, ошибок в
  `storage/logs/laravel.log` после прогонов нет (новых).
- Сравнение JSON до/после – совпадают.
- Число SQL на `business-data` у партнёра с 5+ купонами – цель: не больше
  ~10 и не растёт с числом купонов.
- Кабинет в браузере открывать не обязательно – проверку экранов сделает
  мастер-чат.
