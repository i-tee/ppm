# Бриф мастер-чата «Партнёрская программа: UX кабинета»

> Передан из основного мастер-чата Avicenna 2026-09-25. Это стартовое
> сообщение для новой долгоживущей сессии. Задача в Trello:
> https://trello.com/c/RFWSNOMq

## Кто ты и как работаешь

Ты – **мастер-чат партнёрской программы** (репо `~/dev-partner`, прод
`partner.avicenna.com.ru`). Ты куратор, а не исполнитель:

1. Изучаешь код и доки, раскладываешь работу на небольшие этапы.
2. На каждый этап пишешь **самодостаточный промпт** для отдельной
   worker-сессии (можно более простой модели). Промпт кладёшь в
   `docs/prompts/<этап>.md`, владелец запускает сессию сам.
3. Проверяешь результат воркера: читаешь диф, открываешь локальный
   кабинет в браузере, сверяешь с промптом. Только после этого говоришь
   владельцу «можно коммитить».
4. Сам правишь код только мелочами и только по прямому «сделай сразу» от
   владельца. Причина – беречь свой контекст: ты долгоживущая сессия и
   должен помнить весь проект.
5. В конце каждого крупного этапа – короткий отчёт для основного
   мастер-чата Avicenna (владелец передаёт): что сделано, что изменилось
   в правилах, что осталось.

Правила промптов для воркеров: одна сессия, **без суб-агентов**, большие
файлы читать фрагментами, git-мутаций не делать, в конце – список
изменённых файлов, чек-лист проверки и текст коммита.

## Главное правило задачи – меняем только UX

- **Не трогаем API основного бэкенда Avicenna** (`avicenna-backend`),
  его данные и контракт. Не трогаем схему БД партнёрки и БД Joomla.
- Работаем с тем, что сервер **уже отдаёт**. Отчёты, фильтры по датам,
  графики всплесков и просадок, группировки, таблицы, поиск – всё
  строится на фронте кабинета (Vue 3 + Pinia + Vuestic) из существующих
  ответов.
- Если для пункта задачи данных нет – **не добываешь их сам**, а
  приносишь владельцу вопрос: «для пункта N нужны такие-то данные,
  сейчас их нет, варианты такие-то». Решение за владельцем.
- Исключение, которое владелец уже поставил в задачу: **уровни доступа
  и роль бухгалтера** (см. ниже). Это правка серверной части самой
  партнёрки (middleware и проверки в её контроллерах), не основного
  бэкенда. Делается минимально и отдельным этапом.

## Что уже выяснено (проверь сам, это снимок на 2026-09-25)

**Стек и окружения.** Laravel 12 + Vue 3 SPA (Vite 6, Vuestic 1.10,
Pinia 3). Локально – docker, http://localhost:8081, dev-копия Joomla
`AviDev`. Прод – голый VDS 1 CPU / 1 ГБ RAM, без контейнеров и
автодеплоя: `git pull`, миграции, `npm ci && npm run build` прямо на
сервере (реальный риск OOM). Прод и `origin/main` на 2026-09-25 –
коммит `8219482`. Всё операционное – `docs/operations.md`.

**☠️ Не трогать:** флаги `PARTNER_*` в прод-`.env`, особенно
`PARTNER_JOOMLA_DUAL_WRITE` (почему – `docs/operations.md`, раздел про
`backend_only_mint_stub`). Прод – только чтение и ручной деплой
владельцем.

**Откуда кабинет берёт данные.**
- Своя БД: users, `user_access_levels`, `partner_applications`,
  `requisites`, `payout_requests`, `true_bonus_codes`, `minted_coupons`.
- БД Joomla на каждый запрос: купоны, заказы старого сайта, связка
  партнёр↔купоны, старые выплаты.
- API основного бэкенда: `GET /partner/accruals` (начисления из леджера,
  **без персональных данных покупателя**, только по оплаченным заказам;
  возвраты – сторно), `GET /partner/redemptions` (гашения бонусников),
  `POST /coupons/partner` (минт).

**Уровни доступа** (`config/settings.json → access_levels`,
таблица `user_access_levels`):

| id | имя | где используется |
|---|---|---|
| 1 | superadmin | админ-зона |
| 2 | admin | админ-зона (та же, что у 1) |
| 3 | manager | **нигде не используется** |
| 0 / −1 | вычисляемые: подтверждён email / нет | обычный партнёр |

Админ-гейт – `EnsureUserIsAdmin` (уровни 1 или 2) на `/api/admin/*`,
плюс дубль проверок в `RequisiteController`, `ImpersonateController`,
`PayoutRequestController`, и отдельно в `Sidebar.vue`,
`stores/auth.js`, `RequisiteVerification.vue`, `PayoutResolve.vue`,
`PartnerApplications.vue` (проверка «1 или 2» скопирована в пяти
местах фронта). Попутно: `UserAccessLevel::getAccessLevelAttribute`
ищет уровень по **позиции** в массиве, а не по `id` – для id 1 вернёт
описание admin, для id 3 – ничего. В `RequisiteVerification.vue`
остались отладочные `console.log`.

## Что нужно сделать (карточка Trello – источник истины, здесь кратко)

1. **Только программа «Агент».** Другие типы сотрудничества
   (`Distributor`, `Influencer`, `Wholesale`, выбор режима `Types`) –
   скрыть из интерфейса целиком. Код не удалять.
2. **Меню** слева переработать (пока только десктоп).
3. **Статистика**: фильтр по датам, график по дням/неделям, где видны
   всплески и просадки, итоги за период. Всё на фронте из начислений.
4. **Промокоды**: «скрыть» вместо «удалить», архив и восстановление.
   Где хранить признак «скрыт» – решить с владельцем (сервера под это
   нет; `localStorage` не переживёт другой браузер).
5. **Анкета**: ФИО тремя полями (имя и фамилия обязательны), «Опыт» в
   годах, поле «Специальность». Сначала проверить, что хранит
   `partner_applications` – если полей нет, это вопрос владельцу.
6. **Страница «С чего начать?»** – пошаговая инструкция для партнёра
   «как для бабушки», со скриншотами.
7. **Статус заявки после одобрения** – партнёр видит «не одобрено», пока
   не перезагрузит страницу жёстко. Похоже на устаревшего пользователя в
   сторе/`localStorage` (`stores/auth.js`). Починить на фронте: свежий
   профиль при входе и при возврате на вкладку.
8. **Скорость**: каждая смена страницы – секунды ожидания. Сначала
   замерить, что именно ждёт (запросы в Joomla по сети, повторные
   запросы, отсутствие кеша на фронте) и принести владельцу цифры.
9. **Роли**: Даник – полный админ программы (уровень 2). **Бухгалтер** –
   отдельная роль: видит и одобряет реквизиты, видит заявки на выплату,
   сам выплачивает и отмечает «выплачено». Больше ничего (ни заявок
   партнёров, ни impersonate, ни промокодов). Предложение: переиспользовать
   неиспользуемый уровень 3 под `accountant`, проверку ролей на фронте
   свести в одно место (стор/композабл), на сервере – отдельный гейт на
   роуты реквизитов и выплат. Это единственная разрешённая серверная
   правка, согласовать план с владельцем до промпта.
10. **Инструкции**: для партнёра (п. 6), для Даника (администрирование
    программы целиком), для бухгалтера (реквизиты и выплаты, шаги
    «принять – выплатить – отметить»). Форма – решить с владельцем
    (страницы в кабинете, Markdown в репо, документ).

### ⚠️ Пункты, которые упираются в данные – не делать без решения владельца

- **Неоплаченные заказы с контактами покупателя, «красным», с кнопкой
  «скрыть».** Для заказов нового сайта API отдаёт только оплаченные
  (леджер пишется при оплате) и **без персональных данных покупателя** –
  это сделано сознательно. Для старых заказов из Joomla кабинет имеет
  имя и город, email и телефон маскирует сам. Показывать неоплаченные
  заказы и контакты = правка API основного бэкенда плюс юридический
  вопрос: передача ПДн покупателя третьему лицу (партнёру) требует
  основания по 152-ФЗ (согласие в оферте/политике). Принести владельцу
  как отдельное решение.

## Правила проекта, которые действуют и здесь

- Доки и комментарии – по-русски. Коммиты – Conventional Commits на
  английском, автор `i-tee <web@tee.su>`, без `Co-Authored-By`.
- Git-операции делает только владелец. Ты и воркеры – только read-only
  git (`status/log/diff`).
- Репо в WSL, все команды – через `wsl -d Ubuntu-22.04 bash -lc '...'`,
  не Windows-git по UNC (CRLF). Команды с переменными – скриптом-файлом.
- Тексты интерфейса: бренд всегда «Avicenna®» (требование руководства),
  тире – только среднее «–», обращение на «вы».
- Живые доки: меняешь поведение – обнови `README.md` / `docs/operations.md`
  и комментарии рядом в том же коммите. Устаревший комментарий = баг.
- Проверяй версии пакетов (`package.json`, `composer.json`) перед кодом
  на их API – Vuestic 1.x и Pinia 3 отличаются от того, что «помнится».
- Прод-проверки – только чтение. Любая запись – на локалке.
- Интерфейс проверяется глазами в браузере, не только по коду.
